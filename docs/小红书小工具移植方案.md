# GRIP 移植小红书小工具 — 可行性评估与移植方案

> 评估日期：2026-10-19
> 依据：`minitool-zip-builder` Skill v1.8.0（已安装至全局 skills 目录）+ [小工具在线文档](https://miniapp-sandbox.xiaohongshu.com/minitool/doc)（在线核验成功，文档更新于 2026-10-13）
> 结论先行：**完整管线（YOLO + SAM 自动识别）不可移植；裁剪为"手动/半自动线路高亮 + 一键发笔记"的小工具可行，且与小红书内容场景天然契合。**

---

## 1. 在线文档核验与新增能力播报

按 Skill 工作流，已将在线文档与随包基线（js-api.md，2026-09-23 快照）比对：

**新增能力（在线文档有、基线无）：**

| 能力 | 说明 | 状态 |
| --- | --- | --- |
| `window.xhs.AI.createModel(...).generateText(...)` | 平台对话模型文本生成（`deepseek-v4-flash` / `dots-3-note-prev`），无需 API key | 内测，需提交 uid 给 appId 加白；每用户每天 100 次；非流式 |

对本项目的意义：可用它**自动生成攀岩笔记文案**（如根据线路颜色/数量生成分享文案），但属内测加白能力，不作为 MVP 依赖。

**能力确认（与本项目强相关）：** 在线文档 §5 明确写道——"依赖 WASM 的加速库（如 Draco / Basis / **ONNX** / 抠图算法库）🔴 不可用"，且"**AI 图像处理等重计算场景仍无法支持（既不能联网调用外部模型，也不能运行 WASM 模型）**"。这一条直接决定了移植边界。

## 2. 容器硬性约束速查

| 约束 | 细则 | 对 GRIP 的影响 |
| --- | --- | --- |
| 纯离线 | 禁止 `fetch`/`XHR`，所有资源打进 zip | 模型无法运行时下载 |
| 包体 | zip ≤ 10 MiB（建议 ≤ 2 MiB） | 三个 ONNX 模型合计 ~72.5 MB，超限 7 倍 |
| 文件类型白名单 | 仅 html/css/js/png/jpg/jpeg/gif/webp/svg/woff/woff2/json | `.onnx` 根本进不了包 |
| **WebAssembly 禁用** | `WebAssembly.*` 编译执行被禁 | ONNX Runtime Web / tract-wasm 路线全灭 |
| Worker 禁用 | Web Worker / SharedWorker / ServiceWorker / OffscreenCanvas+Worker | 计算只能在主线程，须分片让出 |
| 脚本形态 | 外置经典脚本，禁内联/`type="module"`/`eval`/`new Function` | 零构建前端思路兼容，需改造 |
| 兼容基线 | JS：ES2017 / Chrome 61；CSS：Chrome 61 基线 + 能力检测增强 | 零构建手写 ES2017 即可，无需引入构建链 |
| 选图 | `<input type="file">` 仅图片/视频 | 满足照片导入；**无法导入 JSON 会话文件** |
| 可用出口 | `postNote`（发笔记）/ `saveImageToPhotosAlbum` / `writeTempFile` | 恰好是内容分享闭环所需 |
| Canvas 2D / WebGL | 完整可用（WebGL 仅纯渲染） | 像素处理与合成无阻碍 |

## 3. 现有模块逐条评估

### 3.1 不可移植（硬性阻断）

| 模块 | 内容 | 阻断原因 |
| --- | --- | --- |
| `detector.rs` | ChalkGPT YOLO11s 岩点检测（tract 推理，36.2 MB ONNX） | WASM 禁用 + 文件类型白名单 + 10 MiB 包体 + 无网络，四重阻断 |
| `sam.rs` | EdgeSAM 分割（encoder 21.1 MB + decoder 15.2 MB） | 同上 |
| `lib.rs` 主路 | YOLO 框提示 SAM ∩ 墙面差分的自动掩码管线 | 依赖上述两者 |
| tract / rayon | ONNX 运行时、并行解码 | 无 WASM、无 Worker |
| `climb-cli` | 批处理 / agent 会话 | 形态不匹配，无意义 |
| Tauri 后端 | `climb-app/src/main.rs` 全部编辑命令 | Rust 无法进容器 |

### 3.2 可移植（纯算法，重写量小）

| 模块 | 内容 | 移植方式 |
| --- | --- | --- |
| `hsv.rs` | RGB↔HSV/Lab、`ab_angle`、`color_name_ab`、`display_rgb` | 纯数学，直接翻译成 JS（~200 行） |
| `cluster.rs` | Lab (a*,b*) 平均链接凝聚聚类 + 黑白灰特判 | 纯数值，直接翻译（~150 行核心） |
| `morph.rs` | dilate / 盒式模糊羽化 | TypedArray 实现，半小时工作量 |
| `conn.rs` | 连通域拆分（BFS/并查集） | 直接翻译 |
| `render.rs` | keep_mask 颜色约束（Lab 色度 ≤20、低饱和放行）、膨胀羽化、双线性放大、灰度混合、`bg_fill` 墙面净化 | 概念与参数全部可复用，掩码来源改为新交互；Canvas 2D `ImageData` 实现 |
| `session.rs` 概念 | 标注持久化 | 改用 Storage API（9.46+）/ localStorage 降级；JSON 体积小，无阻碍 |
| GUI 交互语义 | 选线/排除/抹除/套索/归组/撤销（含"已选线路时圈选直接并入、不做颜色校验"的既定语义） | 照搬产品语义，JS 重写事件层 |
| 零构建前端理念 | `climb-app/ui/` 已是原生 HTML/CSS/JS（app.js 24 KB） | 架构理念一致，但 `window.__TAURI__` 桥全部要换成 JS 内核 |

### 3.3 需要替代设计（核心难点）

| 原能力 | 替代方案 |
| --- | --- |
| YOLO 自动框出岩点 | **A.（MVP 推荐）纯手动点选**：点击岩点 → 以种子点做局部 Lab 颜色区域生长出掩码。**B.（增强）墙面差分候选**：复用 GRIP 已有的"无 YOLO 回退路径"思路（`build_wall_field` 墙面场 + 局部 Lab 差分 + 连通域）预筛候选点，点击吸附最近候选。该回退路径在桌面版已验证可用，纯像素统计，JS 可实现；精度低于 YOLO，只做辅助不做自动。**C.** SLIC 超像素辅助圈选（备选） |
| SAM 精确轮廓 | 区域生长掩码 + `morph` 膨胀/羽化修饰边缘；对"整点性"要求降级（用户点选本来就表达了意图） |
| 颜色聚类分线 | `cluster.rs` 原样移植，作用于用户点选/圈选出的岩点集合，不是全图自动检测结果 |

## 4. 可行性结论

**不可行：把 GRIP 完整管线搬进小工具。** 自动检测（YOLO）+ 精确分割（SAM）依赖 ONNX 模型推理，容器在 WASM、文件类型、包体、联网四个维度同时封死，在线文档亦明确点名 ONNX 不可用。此方向无绕路。

**可行：裁剪为"攀岩线路高亮"创作小工具**，产品公式不变——*选中线路保色、其余灰度*——但岩点来源从"AI 自动"改为"用户点选 + 颜色辅助"。这反而是小工具的合理定位：

1. **输入顺**：`input type="file"` 选照片 / `getUserMedia` 拍照，移动端即发即拍。
2. **处理可行**：所有保留下来的算法（Lab 聚类、颜色约束渲染、形态学）都是纯像素数学，ES2017 + TypedArray + Canvas 2D 足够；~900px 分析分辨率下移动端主线程分片计算预计 1–3 s，可接受。
3. **出口闭环（小工具独占价值）**：`postNote` 一键把成品图带进发布页、`saveImageToPhotosAlbum` 存相册、`interactionOpenApi` 带图评论 PK——桌面版没有的传播闭环，恰是小工具的核心动机。
4. **包体无压力**：纯代码 + 图标预计 < 500 KB，远低于 2 MiB 建议线。

## 5. 移植方案

### 5.1 产品形态（MVP 功能集）

名称建议：**「线路高亮」**。单页三态流程：

1. **导入**：选图 / 拍照 → 降采样至分析分辨率（长边 ~900px）。
2. **标注**：
   - 点击岩点 → 区域生长取掩码，加入当前线路；
   - 套索圈选 → 圈内候选并入当前线路（沿用 GRIP 既定归组语义：已选线路时直接并入，不做颜色校验）；
   - 「按颜色选线」：点一下任意岩点 → 全局 Lab 聚类找同色组，一键成线；
   - 排除 / 抹除（语义沿用 ADR 0002：抹除=误检满强度抹平、排除=仅灰度化）、撤销。
3. **导出**：保色渲染（分析分辨率合成 keep_mask → 双线性放大 → 全分辨率灰度混合）→ 预览 → `writeTempFile` → `postNote` / 存相册。

### 5.2 技术架构（Rust → JS 映射）

```
zip 根
├── index.html          # 唯一入口（viewport-fit=cover，脚本外置）
└── assets/
    ├── style.css       # Chrome 61 基线层 + @supports 增强层
    ├── js/color.js     # ← hsv.rs：RGB↔Lab/HSV、色度角、颜色命名
    ├── js/morph.js     # ← morph.rs：dilate / box blur（TypedArray）
    ├── js/conn.js      # ← conn.rs：连通域 BFS
    ├── js/cluster.js   # ← cluster.rs：Lab (a*,b*) 平均链接凝聚聚类
    ├── js/detect.js    # 区域生长取点 + （实验开关）墙面差分候选
    ├── js/render.js    # ← render.rs：keep_mask 颜色约束、羽化、灰度混合、bg_fill
    ├── js/store.js     # Storage API(9.46+) / localStorage 降级封装
    ├── js/xhs.js       # window.xhs 能力检测、postNote/saveImageToPhotosAlbum/writeTempFile
    └── js/app.js       # 视图状态机 + 触摸交互（pointer events）+ 撤销栈
```

- 多个经典 `<script src>` 按依赖顺序加载，`window` 命名空间协作（容器禁 module）。
- 直接手写 ES2017 交付，**不引入构建链**（项目本无前端构建链，符合 js-compatibility.md 的"无构建链"分支）。
- 算法参数直接沿用 GRIP 已调好的魔法数：`color_tol_ab=14`、渲染色度约束 ≤20、`colored` 门限 sat≥0.22 && v≥0.10、外扩/羽化半径等，保持两端效果口径一致。

### 5.3 性能设计（无 Worker 的主线程策略）

- 分析分辨率固定长边 900px（≈54 万像素）：Lab 转换、区域生长、聚类均为 O(n)，单次 < 300 ms。
- 重计算分片：`render` 全分辨率合成按行块切分，块间 `setTimeout(0)` 让出主线程，避免 > 200 ms 长任务卡死触摸。
- 全分辨率缓冲：4000×3000 RGBA ≈ 48 MB，同屏最多保留 2 份（原图 + 合成），预览用分析分辨率，仅导出时才做全分辨率合成；低端机导出分辨率可降到长边 2000px。
- `visibilitychange` 时中止进行中的分片计算。
- 交互重渲染只重算分析分辨率预览（< 100 ms），不碰全分辨率。

### 5.4 平台能力接入

| 能力 | 用法 | 版本门槛 |
| --- | --- | --- |
| 保存/分享成品 | `writeTempFile` → `postNote`（photo_publish）/ `saveImageToPhotosAlbum` | 无 |
| 会话持久化 | Storage API 存标注 JSON（岩点坐标、颜色组、排除/抹除集），localStorage 降级 | 9.46+ |
| 笔记文案（可选增强） | `window.xhs.AI` 生成分享文案 | 内测加白，每日 100 次；未加白时隐藏入口 |
| 带图评论 PK（可选） | `interactionOpenApi` 携成品图唤起评论区 | 9.49+ |

所有 `window.xhs` 调用前先判空，普通浏览器/低版本环境隐藏对应按钮（能力检测，不按 UA 分支）。

### 5.5 合规自查要点（交付前逐项过）

- 无 `fetch`/XHR/`eval`/`new Function`/`WebAssembly`/`Worker`/内联脚本/行内事件/`type="module"`；
- 资源全部相对路径、全部在 zip 内；无 `<base>`、无 iframe、无外部 URL；
- JS 不超 ES2017 语法；CSS 走 Chrome 61 基线 + 能力检测增强（Flex gap 用行为检测）；
- zip 根直接是 `index.html`（进目录压缩内容而非目录本身）；
- 跑 `audit_artifact.py` / `audit_artifact.mjs` 双门禁之一 + 人工清单；
- **浏览器直运行结果不作为验收依据**：交付后须在创服平台模拟器 + Android 真机扫码 + iOS 真机扫码三端验证（待用户执行）。

## 7. 风险与开放问题

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 无 YOLO/SAM 后"自动识别"卖点消失 | 用户预期落差 | 产品定位即"手动高亮创作工具"，不承诺自动；「按颜色选线」保留半自动体验 |
| 区域生长掩码边缘粗糙（对比 SAM 轮廓） | 保色边缘不精致 | 膨胀+羽化修饰；GRIP 基线中回退路径（墙面差分 blob）本就可达 7 分水准 |
| 移动端内存（全分辨率双缓冲 ~100 MB） | 低端机崩溃 | 导出降档开关、缓冲即弃、分片合成 |
| 墙面差分候选检测误检多（复杂墙面） | 辅助点击吸附漂移 | 默认关闭，实验开关灰度；不影响纯手动主路径 |
| AI 文案内测加白不确定 | 增强功能跳票 | 不进 MVP 关键路径 |
| 会话无法跨端迁移（小工具与桌面版隔离） | 双端用户重复劳动 | 接受现状；小工具定位为独立轻量场景 |
| Chrome 61 真机表现 | 兼容性问题 | 按 css/js-compatibility.md 基线 + 增强分层开发，三端验证列入 M4 |

## 8. 与桌面版的关系

小工具不是 GRIP 的替代品，而是**下游分发出口**：桌面版继续服务"精确分析 + 批量处理"的专业场景；小工具服务"随手拍 → 高亮 → 发笔记"的传播场景。两者共享算法口径（颜色空间、聚类容差、渲染约束参数），未来若小红书开放图像类平台能力（当前仅文本 AI），再评估把 YOLO/SAM 以平台能力形式接入。
